持久化的 Agent 对象

这段代码解释了为什么团队成员会“记得队友之前说过什么”。

 151     def __init__(self, name, role):
 152         self.name = name
 153         self.role = role
 154         self.inbox = []  # 通信通道：其他 Agent 发来的消息
 155         self.messages = [  # 持久记忆：跨多次 chat() 保持
 156             {
 157                 "role": "system",
 158                 "content": f"You are {name}, a {role}. Be concise and focused.",
 159             }
 160         ]
 161         print(f"  [创建] {name} ({role})")

 163     def receive(self, sender, message):
 164         """核心 3: 通信通道 —— 接收来自其他 Agent 的消息"""
 165         self.inbox.append({"from": sender, "content": message})

 167     def chat(self, task):
 168         """
 169         核心 1: 持久记忆 —— 每次 chat() 的对话都累积在 self.messages 中
 170         第二次 chat() 时，Agent 还记得第一次做了什么

 172         # 如果 inbox 有新消息，先注入
 173         if self.inbox:
 174             mail = "\n".join(f"[来自 {m['from']}]: {m['content']}" for m in self.inbox)

Team 管理生命周期与通信

招募、广播、解散，这里就是多智能体协作最小骨架。

看 GitHub 行号 
 219 class Team:
 220     def __init__(self):
 221         self.agents = {}  # name → Agent
 222
 223     def hire(self, name, role):
 224         """招募：创建一个持久 Agent"""
 225         agent = Agent(name, role)
 226         self.agents[name] = agent
 227         return agent
 228
 229     def send(self, from_name, to_name, message):
 230         """核心 3: Agent 之间的通信通道"""
 231         if to_name not in self.agents:
 232             return f"Error: {to_name} not found"
 233         self.agents[to_name].receive(from_name, message)
 234         print(f"  [消息] {from_name} → {to_name}: {message[:60]}...")
 235
 236     def broadcast(self, from_name, message):
 237         """广播：给团队所有其他人发消息"""
 238         for name, agent in self.agents.items():
 239             if name != from_name:
 240                 agent.receive(from_name, message)
 241         print(f"  [广播] {from_name} → 全体: {message[:60]}...")
 242
 243     def disband(self):
 244         """解散：所有 Agent 生命周期结束"""
 245         names = list(self.agents.keys())
 246         self.agents.clear()
 247         print(f"  [解散] 团队已解散 ({', '.join(names)})")

再看它怎么跑

把“团队协作”讲成一种可落地的软件结构，而不是抽象概念。

演示命令

python agent/05-teams/agent-teams.py "创建一个 TODO 应用，包含 Python 后端和 HTML 前端"
  • 启动后会先由 `plan_team()` 拆出成员与分工。
  • 每个 Agent 都保留自己的 `messages` 和记忆，不会执行一次就消失。
  • 成员完成后通过 `broadcast()` 把信息发给队友，最后 reviewer 再做检查。

Try It

自己试一轮

讲 1 小时时，把多智能体团队讲成“带 reviewer 的协作流水线”最容易让大家记住。

  1. 把 `plan_team()` 固定成两开发一审查的三人团队。
  2. 在执行中手动插入一次 `send()`，演示点对点消息和广播的区别。
  3. 让 reviewer 再执行一次 `chat()`，体会持久记忆如何带来二次审查。

Takeaway

这一讲会看懂什么

  • 明白 Team 比 SubAgent 多出来的是持久身份与通信。
  • 能用 `inbox` 这种极简单模型解释 Agent 间消息传递。
  • 知道为什么 reviewer 是分享里最好展示团队价值的角色。

Share Track

分享只讲这 3 件事

  • 多智能体最重要的不是人数，而是角色和生命周期。
  • Agent 的 `inbox` 足够简单，却已经能支持很多协作场景。
  • 团队越大不一定越好，真正有价值的是信息流变清晰。

Misread

容易误解

  • 如果每个角色都很泛，最后只是多个普通助手轮流说话。
  • 消息太多时又会重新触发上下文压力。
  • 团队协作如果没有 reviewer，很难展示“协作带来的质量提升”。
