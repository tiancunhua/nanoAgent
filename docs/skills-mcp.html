Scenario

什么时候会用到

团队有自己的代码规范、有内部 API、还希望不同项目用不同能力，但又不愿意把这些都硬写进脚本里。能力外置，就是把这些差异从代码里抽到项目目录中。

 241 def parse_markdown_skill(path):
 242     content = path.read_text(encoding="utf-8")
 243     metadata = {}
 244     body = content
 245     if content.startswith("---\n"):
 246         end = content.find("\n---", 4)
 247         if end != -1:
 248             frontmatter = content[4:end].strip()
 249             body = content[end + 4 :].strip()
 250             for line in frontmatter.splitlines():
 251                 if ":" not in line:
 252                     continue
 253                 key, value = line.split(":", 1)
 254                 metadata[key.strip()] = value.strip()
 255     name = metadata.get(
 256         "name", path.parent.name if path.name == "SKILL.md" else path.stem
 257     )
 258     triggers = [
 259         trigger.strip().lower()
 260         for trigger in metadata.get("triggers", "").split(",")
 261         if trigger.strip()
 262     ]
 263     return {
 264         "name": name,
 265         "description": metadata.get("description", ""),
 266         "when_to_use": metadata.get("when_to_use", ""),
 267         "triggers": triggers,
 268         "path": str(path),
 269         "content": body,
 270     }

 273 def format_skill_for_prompt(skill):
 274     lines = [
 275         f"## {skill['name']}",
 276         f"Source: {skill['path']}",
 277         f"Description: {skill.get('description', '')}",
 278     ]
 279     when_to_use = skill.get("when_to_use")
 280     if when_to_use:
 281         lines.append(f"When to use: {when_to_use}")
 282     if skill.get("triggers"):
 283         lines.append(f"Triggers: {', '.join(skill['triggers'])}")
 284     lines.append(skill["content"])
 285     return "\n".join(lines)

看源文件 
---
name: todo_prioritizer
description: 给候选修复项排序：安全风险第一，阻塞运行第二，核心功能第三，文档或示例最后；如果只允许输出 3 项，舍弃文档或示例项，并保持输出简洁。
when_to_use: 当任务要求整理修复顺序、挑选优先级或从多个候选问题中选出下一步行动时使用。
triggers: todo_prioritizer, 修复顺序, 优先级, 候选修复项, 最该先修
---

# Todo Prioritizer

## Use When

当任务要求整理修复顺序、挑选优先级，或从多个候选问题中选出下一步行动时使用。

## Priority Order

1. 安全风险
2. 阻塞运行
3. 核心功能
4. 文档或示例

## Steps

1. 先识别每个候选项属于安全风险、阻塞运行、核心功能、文档示例中的哪一类。
2. 按安全风险、阻塞运行、核心功能、文档示例的顺序排序。
3. 如果题目要求最多 3 项，只输出前三项。
4. 每项用“优先级 - 类别 - 事项”的短格式。
5. 最后用一句话说明被舍弃项为什么靠后。

## Output Example

```text
1. 优先级 - 安全风险 - 删除用户接口缺少权限校验
2. 优先级 - 阻塞运行 - 应用启动时报错无法运行
3. 优先级 - 核心功能 - 搜索结果分页偶尔重复

舍弃项：README 示例命令有错别字（文档或示例类，优先级最低）。
```

  • 第一屏先看三类日志：[Rules] Loaded ...、[Skills] Loaded 1 skill files: todo_prioritizer、[MCP] Loaded ...。
  • 第一条命令观察 [Tool] project_guide(...)，用真实工具调用证明 MCP 已进入 tools。
  • 第二条命令观察回答是否遵守 .agent/rules/demo-style.md 的格式要求，用输出格式证明 Rule 生效。
  • 第三条命令只给 4 个候选项：安全风险、阻塞运行、核心功能、文档示例各 1 个；正确结果应优先输出 B、C、D，并舍弃 A。
  • DEFAULT_MAX_ITERATIONS = 10 只是为了保证现场演示有足够轮次完成工具调用与结论生成。

  3. 打开 .agent/mcp.json，将 project_guide 改名或禁用，观察 [MCP] 日志和工具列表变化。

Takeaway

这一讲会看懂什么

  • 知道 Skill 负责补充知识，Rule 负责约束行为，MCP 负责接入外部工具。
  • 能识别 Rules、Skills、MCP 各自的加载来源，以及它们如何拼装进上下文与工具列表。
  • 理解工程化 Agent 的关键不在于继续堆内置逻辑，而在于能力与约束的外置。

Key Points

三个核心要点

  • 最小 Rule 用来约束输出行为，最小 Skill 用来补充任务知识，最小 MCP 用来扩展可调用工具。
  • Rules 与 Skills 最终进入 prompt，MCP 最终进入 tools，注入位置不同，作用也不同。
  • DEFAULT_MAX_ITERATIONS = 10 是演示友好值，能避免复杂搜索在结论前过早中断。

Pitfalls

容易误解

  • 将所有约束都堆入 Rule，会模糊职责边界，模型也更难稳定执行。
  • Skills 过多会稀释上下文，MCP 工具过多会降低模型的工具选择准确率。
  • 迭代次数调高会改善演示完整度，但也会增加 token 成本与执行时间。
  • 规则、技能、工具描述互相冲突时，模型表现会显著不稳定。
