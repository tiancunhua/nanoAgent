01. 底层原理，约 100 行

没有框架，直接运行 Agent 的最小闭环：模型选择工具，代码执行工具，结果回填给模型。

工具调用Agent Loop最小实现
从场景开始 直接看代码

Scenario

什么时候会用到

把“帮我创建 hello.txt，内容写 Hello Agent”这类任务交给 ChatGPT，它只能给你建议；如果希望它真的在文件系统里创建出这个文件，就需要在模型外面再裹一层能调用工具、能循环执行的代码。

Code First

先看关键代码

聚焦决定行为的核心实现，再结合终端结果对照，能更直观地理解 Agent 的工作方式。

最小 Agent 循环

围绕这二十余行展开：请求模型、获取 tool call、执行工具、回填结果、进入下一轮。

看 GitHub 行号 
  84 def run_agent(user_message, max_iterations=5):
  85     """运行 Agent，直到模型直接回答，或达到最大循环次数。"""
  86     # messages 就是 Agent 的短期记忆；每次模型调用都会看到完整历史。
  87     messages = [
  88         {"role": "system", "content": "You are a helpful assistant. Be concise."},
  89         {"role": "user", "content": user_message},
  90     ]
  91
  92     # 每轮只有两种结果：模型直接回答，或要求执行一个/多个工具。
  93     for _ in range(max_iterations):
  94         response = client.chat.completions.create(
  95             model=os.environ.get("OPENAI_MODEL", "gpt-4o-mini"),
  96             messages=messages,
  97             tools=tools,
  98         )
  99         message = response.choices[0].message
 100
 101         # 必须先保存 assistant 消息，其中包含模型发出的 tool_call id。
 102         messages.append(message)
 103
 104         # 没有工具调用，说明模型认为任务已经完成。
 105         if not message.tool_calls:
 106             return message.content
 107
 108         for tool_call in message.tool_calls:
 109             name = tool_call.function.name
 110             # OpenAI 协议中的 arguments 是 JSON 字符串，要先还原成参数字典。
 111             args = json.loads(tool_call.function.arguments)
 112             print(f"[Tool] {name}({args})")
 113             if name not in functions:
 114                 result = f"Error: Unknown tool '{name}'"
 115             else:
 116                 result = functions[name](**args)
 117
 118             # tool_call_id 将执行结果和模型刚才的请求配对。
 119             # 写回 messages 后，模型下一轮才能根据这个“观察”继续判断。
 120             messages.append({"role": "tool", "tool_call_id": tool_call.id, "content": result})
 121
 122     # 上限用于防止模型陷入无限工具调用，并不是正常完成条件。
 123     return "Max iterations reached"

工具映射到真实函数

Tool 并非抽象概念，最终会映射到真实函数；模型选中的名字就在这里被执行。

看 GitHub 行号 
  61 def execute_bash(command):
  62     """运行 shell 命令，并把标准输出和错误输出都返回给模型。"""
  63     result = subprocess.run(command, shell=True, capture_output=True, text=True)
  64     return result.stdout + result.stderr
  65
  66
  67 def read_file(path):
  68     """读取文本文件，让模型能够观察本地文件内容。"""
  69     with open(path, "r") as f:
  70         return f.read()
  71
  72
  73 def write_file(path, content):
  74     """写入文本文件，让模型的决定真正作用到本地环境。"""
  75     with open(path, "w") as f:
  76         f.write(content)
  77     return f"Wrote to {path}"
  78

再看它怎么跑

现场观察 Agent 不只是输出文字，而是真实地改动了文件系统。

Try It

自己试一轮

将其视作一台能自主选择工具的任务执行器，而非聊天窗口。

  1. 将 max_iterations 改为 2，观察复杂任务如何被提前中断。
  2. 临时从 tools 中移除 write_file，再要求 Agent 写文件，观察其无法完成的原因。
  3. 让 Agent 连续执行“写文件 + 读文件”两个动作，体会循环结构的必要性。
  4. 为 execute_bash 补充更清晰的描述，观察模型是否更易选中正确工具。

Takeaway

这一讲会看懂什么

  • 能解释 Agent 与 Chat 的本质区别。
  • 能看懂 tools、functions、messages 与循环之间的关系。
  • 理解 Tool 是模型可见的能力声明，而非模型自行生成的命令。
  • 明确 Agent 的执行权由代码掌握，不在模型一侧。

Key Points

三个核心要点

  • 循环：Agent 并非只响应一次，而是在每一轮中决定是否继续行动。
  • LLM 输出的是结构化调用意图，并不直接执行系统命令。
  • Tool：tools 是模型看到的能力清单，functions 才是真正落地执行的代码。

Pitfalls

容易误解

  • 仅实现 Python 函数而未注册到 tools，模型无法感知该能力的存在。
  • execute_bash 权限过大，后续需要补充安全边界。
  • 工具报错同样需要回填给模型，否则模型无法自我修正。
  • 只堆叠工具而不设计循环，最终会退化为普通问答。
